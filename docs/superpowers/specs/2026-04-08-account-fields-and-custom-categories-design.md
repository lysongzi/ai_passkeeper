# PassKeeper 账号字段扩展与自定义分类设计文档

## 背景

当前 PassKeeper 的单条账号记录主要包含标题、用户名、密码、分类、备注，以及创建/更新时间等系统字段。随着账号信息管理需求提升，现有结构存在两个不足：

1. 缺少手机号、邮箱这类常用登录辅助信息，用户无法在应用中完整保存一条账号的常见登录资料。
2. 分类体系目前以内置分类为主，无法根据个人使用习惯扩展，影响整理与筛选效率。

本次迭代需要在不破坏现有密码存储、安全流程和整体 UI 架构的前提下，扩展账号字段、统一三个核心场景的展示与校验规则，并引入用户自定义分类能力。

## 目标

1. 为账号记录新增手机号、邮箱两个选填字段，并在新增页、编辑页、详情页完整支持。
2. 统一新增页、编辑页、详情页中的字段文案、字段顺序、必填/选填展示规则。
3. 让手机号、邮箱参与搜索，但不增加列表页展示负担。
4. 支持在设置中管理用户自定义分类，并在账号编辑与主页筛选中使用。
5. 保持系统内置分类不可删除，同时允许用户自定义分类新增、编辑、删除。
6. 将新增能力纳入多语言体系，保证中英文等语言环境下 UI 文案一致可维护。

## 非目标

1. 本次不重构密码加密、解密、安全认证流程。
2. 本次不扩展附件、自定义字段、TOTP、历史密码等更复杂的账号字段。
3. 本次不在列表页展示手机号或邮箱。
4. 本次不实现“删除已被使用的自定义分类时自动迁移账号分类”的高级逻辑。
5. 本次不为用户自定义分类名称提供自动翻译或多语言别名功能。

## 现状分析

### 当前账号字段

当前 `PasswordItem` / `DecryptedPasswordItem` 的核心业务字段为：
- `category`
- `title`
- `username`
- `password` / `encryptedPassword`
- `notes`

系统附带字段为：
- `id`
- `createdAt`
- `updatedAt`
- `searchIndex`

### 当前页面场景

1. **新增页**：支持标题、用户名、密码、分类、备注。
2. **编辑页**：与新增页字段大体一致。
3. **详情页**：展示用户名、密码、备注，并支持编辑保存。
4. **主页面**：支持按分类浏览与搜索，但搜索维度主要覆盖标题、用户名、分类。
5. **设置页**：当前没有自定义分类管理入口。

### 当前分类体系限制

当前分类体系主要依赖固定枚举 `PasswordCategory`，适合已有内置分类展示，但不适合用户侧动态管理，也不适合设置页 CRUD 场景。

## 设计原则

### 原则 1：优先平滑扩展现有模型

本次优先在现有数据模型和页面结构上进行增量扩展，而不是整体重写账号体系。

### 原则 2：页面一致性优先于局部便捷实现

新增页、编辑页、详情页必须形成一套统一字段表达规则，避免同一字段在不同场景中名称、顺序、必填提示不一致。

### 原则 3：分类要区分“系统内置”和“用户自定义”

系统分类用于稳定的默认体验；用户自定义分类用于个性化扩展。两者权限边界必须清晰。

### 原则 4：尽量保持旧数据可兼容

已有账号记录和现有分类不能因本次迭代而失效。迁移应当向后兼容，默认值和兜底行为要明确。

## 方案对比

### 方案 A：最小侵入式扩展（推荐）

做法：
- 直接在账号模型和数据库表中新增手机号、邮箱字段。
- 保留现有系统分类定义，同时新增一套自定义分类存储。
- 页面中的分类选项、筛选源改为“系统分类 + 自定义分类”的合并结果。

优点：
- 改动边界清晰，风险可控。
- 对当前 ViewModel、Repository、UI 结构侵入较小。
- 更适合本次需求范围。

缺点：
- 分类体系仍然是“内置枚举 + 用户数据”的混合结构。

### 方案 B：完全数据化分类体系

做法：
- 将系统分类也下沉成统一数据模型，彻底摆脱当前枚举主导方式。

优点：
- 长期扩展性更强。

缺点：
- 当前改动面过大，牵涉现有筛选、文案、本地化与迁移更多逻辑。
- 超出本轮迭代必要范围。

### 结论

采用 **方案 A：最小侵入式扩展**。

## 详细设计

## 一、账号字段扩展设计

### 1. 新增字段

在账号记录中新增：
- `phoneNumber`
- `email`

设计约束：
- 两者均为选填。
- 存储层建议使用空字符串作为默认值，而不是可选类型。
- 这样可与现有 `notes` 设计保持一致，降低 UI 和数据库处理复杂度。

### 2. 字段顺序统一

新增页、编辑页、详情页统一字段顺序为：
1. 标题（必填）
2. 用户名（必填）
3. 密码（必填）
4. 分类（必填）
5. 手机号（选填）
6. 邮箱（选填）
7. 备注（选填）

手机号和邮箱固定放在“分类”和“备注”之间。

### 3. 三场景文案统一

统一的字段命名与展示规则：
- 标题
- 用户名
- 密码
- 分类
- 手机号
- 邮箱
- 备注

统一的必填/选填规则：
- 标题、用户名、密码、分类：必填
- 手机号、邮箱、备注：选填

统一的展示要求：
- 新增页与编辑页使用同一套字段顺序、标题与必填/选填说明。
- 详情页在阅读态和编辑态保持相同字段排序，避免认知跳转。

### 4. 详情页展示规则

- 非编辑态下，手机号和邮箱如果为空，可不展示具体值内容区域，或展示统一的空值表现。
- 编辑态下应始终可编辑这两个字段。
- 由于本次重点是统一而不是增加冗余，推荐非编辑态对空字段使用简洁空态，不在视觉上过度占位。

### 5. 列表页规则

- 手机号与邮箱不在主列表页展示。
- 列表页继续保持轻量摘要视图，避免信息密度过高。

## 二、校验设计

### 1. 邮箱校验

规则：
- 空值允许通过。
- 非空时必须符合基础邮箱格式。
- 不追求 RFC 级别复杂度，但需拦截明显非法输入。

触发时机：
- 保存时校验并阻止提交。
- 若页面已有错误提示机制，沿用统一错误提示出口。

### 2. 手机号校验

规则：
- 空值允许通过。
- 非空时采用宽松校验。
- 允许字符包含数字、空格、`+`、`-`、`(`、`)`。
- 去除分隔字符后，长度需满足合理区间，避免过短或明显异常。

触发时机：
- 保存时校验并阻止提交。

### 3. 错误反馈

新增错误文案需要明确区分：
- 邮箱格式错误
- 手机号格式错误

不建议将两者混成笼统的“表单错误”，以方便用户快速纠正。

## 三、搜索设计

### 1. 搜索范围扩展

在现有搜索基础上增加以下字段：
- 手机号
- 邮箱

### 2. 搜索行为

用户输入：
- 手机号片段时，可命中相应账号。
- 邮箱片段时，可命中相应账号。

### 3. 索引维护

若现有 `searchIndex` 继续保留，应将手机号和邮箱纳入生成逻辑。
若当前实现以 SQLite 查询字段为主，则数据库查询条件应同步扩展。

推荐两者都更新：
- 模型侧 `searchIndex` 生成逻辑纳入新字段
- 数据库层搜索查询也同步覆盖新字段

这样可兼顾当前代码风格与未来扩展一致性。

## 四、自定义分类设计

### 1. 分类来源模型

分类分为两类：
1. **系统内置分类**
2. **用户自定义分类**

系统内置分类：
- 沿用当前已有分类集合
- 不允许编辑名称
- 不允许删除

用户自定义分类：
- 由用户在设置页管理
- 支持新增、编辑、删除

### 2. 设置页入口

在设置页新增“分类管理”或等价入口，用于展示：
- 系统分类列表（只读）
- 自定义分类列表（可增删改）

该页面或模块至少需要支持：
- 新增自定义分类
- 编辑已有自定义分类名称
- 删除自定义分类

### 3. 新增/编辑页接入

账号新增页与编辑页中的分类选择器，其数据源改为：
- 系统分类
- 自定义分类

两类分类应在同一个选择体系下可用，用户无需感知底层来源差异；但在设置管理页面中需要区分权限。

### 4. 主页面筛选接入

主页面中的分类筛选项应增加自定义分类，以支持：
- 快捷过滤某个自定义分类下的账号

筛选体验应保持与当前主页面一致，不新增额外复杂操作。

### 5. 删除约束

已确认规则：
- **如果某自定义分类正在被账号使用，则禁止删除。**
- 删除时应给出明确提示，告知用户先修改相关账号分类后再删除。

这是本次版本的安全策略，可避免删除后账号记录落入未知分类状态。

## 五、存储与迁移设计

### 1. 账号表迁移

现有 `passwords` 表新增两列：
- `phoneNumber`
- `email`

默认值：空字符串。

要求：
- 对已有本地数据库兼容。
- 应通过 schema migration 或初始化补齐机制确保老用户升级后可正常读取旧数据。

### 2. 自定义分类存储

建议新增独立的分类存储结构，而不是将自定义分类混入设置字符串。

推荐最小结构包含：
- `id`
- `name`
- `createdAt`
- `updatedAt`

如需区分类型，可通过数据来源或模型属性标识自定义分类。

### 3. 旧数据兼容

- 旧账号记录默认没有手机号和邮箱，读取时视为空。
- 旧账号的分类仍按原逻辑展示。
- 新增自定义分类能力不影响历史账号的正常浏览与编辑。

## 六、多语言设计

### 1. 纳入本地化的内容

以下内容必须接入现有 i18n 体系：
- 手机号
- 邮箱
- 对应 placeholder
- 必填/选填文案
- 邮箱格式错误提示
- 手机号格式错误提示
- 分类管理入口
- 新增分类 / 编辑分类 / 删除分类
- 系统分类 / 自定义分类
- 删除受限提示

### 2. 自定义分类名称策略

自定义分类名称属于用户输入数据：
- 按用户原始输入保存与展示
- 不进行自动翻译
- 不要求在不同语言环境下维护别名

系统内置分类名称则继续沿用本地化 key 驱动展示。

## 七、UI 与交互设计

### 1. 新增页与编辑页

需要完成：
- 新增手机号、邮箱输入项
- 统一字段区的标题样式与必填/选填说明
- 分类与备注之间插入手机号、邮箱

### 2. 详情页

需要完成：
- 在详情信息区插入手机号、邮箱
- 编辑时可修改，保存时参与校验
- 与新增/编辑页保持统一顺序和命名

### 3. 设置页

需要完成：
- 新增自定义分类管理入口或管理区
- 可区分系统分类与自定义分类
- 自定义分类支持新增、编辑、删除
- 删除使用中分类时显示受限提示

### 4. 主页面

需要完成：
- 分类筛选源改为支持自定义分类
- 不改变主列表项展示结构

## 九、研发拆分建议

本次可以拆成两个实现方向并行推进：

### 方向 A：账号字段扩展与三场景统一

负责内容：
- 账号模型新增手机号、邮箱
- 数据库存储迁移
- 搜索扩展
- 表单校验
- 新增/编辑/详情页统一字段顺序与文案

### 方向 B：自定义分类体系

负责内容：
- 自定义分类数据模型与存储
- 设置页分类管理
- 新增/编辑页分类选择数据源扩展
- 主页面分类筛选接入
- 多语言文案补充

### 集成阶段

由主线程完成：
- 两条实现线合并
- 构建验证
- 回归测试
- 交互一致性检查

## 验收标准

1. 单条账号记录支持保存手机号、邮箱，且两者为选填。
2. 新增页、编辑页、详情页都能展示并编辑手机号、邮箱。
3. 三个场景中的字段命名、顺序、必填/选填标识保持一致。
4. 手机号、邮箱可参与搜索，但列表页不展示。
5. 设置页可以管理用户自定义分类。
6. 自定义分类可在账号分类选择器中使用，并可在主页面筛选。
7. 系统内置分类不可删除。
8. 自定义分类支持新增、编辑、删除；若分类被账号使用则禁止删除。
9. 新增功能文案支持多语言；自定义分类名称按用户输入原样展示。
10. 老数据升级后可正常使用，不因 schema 变更导致已有账号不可读。
